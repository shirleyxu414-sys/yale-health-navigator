Hi, I'm Shirley. Yale Health Navigator is a web app for Yale members who need care but do not know where to start. You type what is going on in plain words, and it gives you the Yale Health line to call, a plan for the call, and a coverage check that quotes Yale's own documents. The code is public on GitHub, and you can clone and run it in about five minutes.

Here is the honest comparison with what people use today. The Yale Health site and PDFs are accurate and complete, but you must know the page and your role. Member Services is a person who can confirm anything, but only Monday to Friday, 8:30 to 5:00. MyChart is good for non-urgent care questions but replies take about two business days. A general chatbot such as ChatGPT is instant and friendly, but it answers from memory, so it can state coverage that is wrong. What is new here is a grounding layer: the model may only quote the rule files for your role, code checks the quote and every number, and the first answer is the line to call. The limits are real too: it is only as good as its rule files, and it cannot know your personal eligibility. Most chatbots try to sound right; this one has to prove it, or say I don't know.
How it works

Three agents and one verifier

Design choice: work is handed over in code, not agent to agent, so each call stays small and every step is logged.

Yale Health Navigator · github.com/shirleyxu414-sys/yale-health-navigator
This is the flow. The screen runs first, in code: emergencies, crisis words, prompt injection and requests to diagnose never reach a model. Then three model calls, each gpt-6-luna with no tools: the router picks the category and the line, the coverage checker reads only your role's rule file plus the common file, and the plan builder writes the timeline and the points to bring up. In between, the verifier, also code, checks citation, quote, numbers and diagnosis words. Handoffs happen in code, not agent to agent, so each call stays small and every step is logged. Chat questions use a separate agent with one tool, lookup_rules, limited to four rounds.

Safety · built in code, before the model

It refuses before it guesses

  • 1Emergency: only "Call 911"
  • 2Injection: 5 of 5 attempts refused
  • 3Diagnosis: refused, sent to a clinician
  • 4Invented facts: quote and numbers checked
  • 5Overspending: 200,000-token session cap

The trade-off: strict checks sometimes say "I don't know" to a correct answer, such as "$0" for "covered at 100%".

The live Safety demo. 495 tests pass.

Safety is built in code so it holds even if the model misbehaves. Emergencies show only the 911 message. Five of five injection attempts are refused with no model call. Diagnosis requests are refused and routed to a clinician. Invented facts: the claim must be a quote from the cited rule and every number must be in it, otherwise the answer becomes I don't know. Overspending: 200,000 input tokens per session and a million per address. The Safety demo page runs all of this live with no tokens, and 495 tests pass. The honest trade-off: strict grounding sometimes rejects a correct answer, for example when the model writes $0 for covered at 100 percent.

What I learned, and what is next

The model is the easy part

Model for judgment, code for rules
3 model calls read and write. Anything checkable runs in code at zero tokens.
Make it quote, then check the quote
Safer than asking nicely, but it sometimes refuses a right answer. I chose safe over smooth.
The rule files are the product
The answers are only as good as about 40 rules. Upkeep, not tokens, is the real running cost.

  • 2Yearly rule review with Yale Health

Who owns it: Yale Health should own the rule files. This app is a front door to them.

Yale Health Navigator · github.com/shirleyxu414-sys/yale-health-navigator
Three lessons. First, use the model for judgment and code for rules: three model calls do the reading and writing, and everything that can be checked deterministically runs in code at zero tokens. Second, make the model quote, then check the quote. Grounding by checking beats grounding by asking nicely. It costs a few false I don't knows, and I chose safe over smooth. Third, the rule files are the product. The answers are only as good as the roughly forty rules behind them, so the real ongoing cost is keeping them true. The dental rule deliberately has no prices because they change every year. So next steps in order of value: a real user test, because it is the biggest unknown; a yearly rule review with Yale Health; hosting with the budget caps so anyone can try it; and prompt caching plus a number-tolerant grounding check to cut cost and false refusals.
